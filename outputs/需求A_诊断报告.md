# 产业场景诊断与AI工作流建议报告

## 一、客户问题概述

本次方案面向项目制科技服务公司的月度经营会场景，定位为“项目经理经营会前AI工作台”。客户的核心痛点不是缺少一个完整项目管理平台，而是项目资料、成本进度数据、客户反馈、验收材料和规则口径分散，导致项目经理在经营会前临时补表、风险发现滞后、报告结论缺少证据链。

本方案将最小验证范围收敛为：用官方项目经营样例数据 P001-P008，形成项目总览、风险分诊、资料缺失清单、月度经营分析草稿和人工复核任务池。AI负责汇聚材料、计算指标、生成草稿和提示复核点；项目经理、财务负责人和审核人保留成本、验收、责任归属和对外承诺的最终确认权。

## 七、AI可做、人工必须做、禁止AI直接做

| 类型 | 内容 |
| --- | --- |
| AI可做 | 汇总项目数据、计算成本/周期指标、标注风险标签、生成月报草稿、列出缺失材料和复核任务 |
| 人工必须做 | 确认成本异常原因、验收材料版本、规则冲突口径、对外沟通措辞和最终经营判断 |
| 禁止AI直接做 | 判定项目亏损、归责到个人或部门、确认验收通过/失败、承诺收益改善、发布对外结论 |

| 感知层 | 项目记录、客户反馈、规则材料 | 按项目编号汇聚材料 | 确认数据口径 | 项目总览 |

| 证据层 | 数据、反馈、规则、历史案例 | 绑定证据路径 | 提交前检查 | 证据地图 |

### 8.1 架构选型说明：为什么不用单次问答

本方案刻意选择**状态机式分层工作流**而非"一句话问AI生成报告"的单次问答模式。原因如下：

**从"裸奔"到"穿甲"——Agentic Scaffolding架构**

单次问答式AI在真实业务中存在三个致命缺陷：输出格式不可控（一次生成的报告可能遗漏关键字段）、幻觉无法拦截（AI可能编造不存在的项目数据或成本数字）、错误无法回退（生成后发现问题只能整体重来）。本方案采用有限状态机（FSM）编排：每一层是一个状态节点，有明确的输入契约、输出契约和状态流转规则。当判断层发现数据口径冲突时，不是"带病生成"，而是回退到感知层补充数据；当人工驳回草稿结论时，不是直接修改文本，而是回退到判断层重新分诊。这种可回退、可降级的架构把脆弱的AI Demo转化为可复核的业务系统。

**防御性AI编程——容错与降级**

每个工作流节点都设计了fallback策略（详见 `workflow.json`）：AI输出崩溃时自动降级为原始数据透传，保证信息不丢失；AI生成越权表述时触发关键词过滤器自动拦截替换；AI计算结果偏差过大时由硬编码规则引擎兜底。系统的底线是：即使AI完全失灵，用户至少能拿到结构化的原始数据和待办清单，而不是一片空白。

**Skill与Memory解耦——可复用的工业级架构**

本方案将AI能力拆分为三层：Skill（Prompt模板，如数据预处理、风险判断链、报告生成——可复用于不同客户）、Memory（项目经营数据、客户反馈——按客户动态注入）、Guardrail（规则与审核清单、主体责任边界——全局约束，不随客户变化）。换一家客户的项目数据，同一套Skill即可运行。这种解耦架构是从一次性交付走向标准化产品的关键。

### 8.2 UX即驾驭：界面设计本身就是AI护栏

本方案的原型界面不是"好看的数据看板"，而是一套**隐形的AI护栏系统**：

| 界面机制 | 护栏效果 |
| --- | --- |
| 预设快捷问题卡片 | 将用户的开放式提问收敛为AI有能力回答的结构化查询，从源头降低幻觉概率 |
| 结构化卡片式AI回复 | 强制AI按"数据→判断→来源→复核提示"固定格式输出，禁止自由文本跑偏 |
| 风险等级筛选按钮 | 用UI约束数据展示维度，比让AI自行决定"展示什么"更可控更可预期 |
| 人工复核操作按钮 | 把AI建议的终审权锚定在人，UI层面保证主体责任不被绕过 |
| 常驻"仅供内部参考"声明 | 从界面层防止AI输出被直接用于对外沟通 |

这种设计理念的核心是：**最好的AI约束不是写在Prompt里让模型"遵守"，而是写在产品交互里让用户"只能这样用"**。

### 8.3 Local-First架构：数据主权的刻意选择

原型提供在线Demo（[https://ucnaluyl2vsy.aiforce.cloud/app/app_4kckzrrhv605x](https://ucnaluyl2vsy.aiforce.cloud/app/app_4kckzrrhv605x)）和本地静态页面两种访问方式。本地版本采用纯静态HTML/CSS/JS实现，数据内嵌，不依赖云端API、账号、密钥或网络服务。这不是3小时限时下的技术妥协，而是面向产业场景的刻意选择：项目经营数据属于企业敏感信息，Local-First架构确保数据不离开企业内网，满足数据主权要求。验证阶段用本地静态页面；规模化后可部署为企业内网Web应用，仍保持数据不出内网的原则。

## 九、P002端到端工作流可执行示例

为避免方案停留在流程图层面，以下用官方样例数据中的 P002 走完整个工作流。

| 流程节点 | P002输入/处理 | 输出结果 | 人工责任 |
| --- | --- | --- | --- |
| 感知层：资料进入 | 项目记录显示 P002 为咨询交付项目，执行中，预算28万元，已发生成本31万元，计划45天，已用42天，验收风险高，质量问题5，满意度3.1；客户反馈为“报告修改次数多，成本超预算仍未提前预警”。 | 形成 P002 项目总览，标注项目数据来源为官方项目记录和客户反馈。 | 项目经理确认项目阶段和数据口径是否最新。 |
| 判断层：风险识别 | 成本使用率=31/28=110.7%；周期使用率=42/45=93.3%；质量问题5且满意度3.1；验收风险高；客户反馈要求人工复核。 | P002 被分诊为“高优先级”，风险项为成本、进度、质量、验收、反馈。 | 财务负责人确认成本超预算原因，项目经理确认交付风险是否属实。 |
| 生成层：报告草稿 | AI把 P002 放入经营会高优先级项目，使用谨慎措辞描述为“建议优先复核”。 | 月报草稿写入：P002需经营会优先讨论，复核成本超预算原因、报告修改次数和交付风险。 | 业务顾问调整表达，避免写成“项目已亏损”或“责任已明确”。 |
| 复核层：人工任务 | P002 涉及成本、交付质量、验收和客户反馈，均属于不可直接对外定稿事项。 | 生成人工复核任务：补充成本明细、报告修改记录、返工说明、客户反馈原文。 | 项目经理、财务负责人、交付负责人共同复核。 |
| 证据层：来源绑定 | 关键结论分别绑定到项目经营样例数据、客户反馈、项目风险判断口径和规则审核清单。 | 证据文件包括 `项目风险计算.csv`、`P002_端到端案例.md`、`规则风险检查.md`。 | 提交前确认路径存在，结论不越权。 |

P002案例说明：AI的价值不是替项目经理给最终责任判断，而是在经营会前把分散数据转成“可解释、可复核、可追溯”的处理队列。人工最终确认后，才可以决定是否进入正式对外报告。

## 十、2-6周轻量化验证路径

1. 第1周：统一项目编号、成本表、验收材料、客户反馈和资料清单字段；用 P001-P008 口径验证计算逻辑。
2. 第2-3周：让项目经理在经营会前使用工作台生成风险分诊和月报草稿，记录人工修改点。
3. 第4-6周：扩展到真实项目样本，跟踪风险提前发现数量、复核任务闭环率、资料缺失项补齐率和月报整理耗时。
4. 验证通过后，再逐步扩展到任务提醒、更多项目类型和真实系统接入。

本方案优先解决客户眼前的经营会准备和风险识别问题，同时保留主体责任边界，避免把3小时验证扩大成完整系统建设。
